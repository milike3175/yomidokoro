# 様式を診断する（書ける県を増やす手順）

県ごとに違うのはルールだけではない。申請書の様式の形も、記号や番号や言い回しも県の数だけある。この手順は、白紙の様式と記載例を Claude が読んで「どこに何をどう書くか」を決め、プログラムで突き合わせ、行政書士が確かめてから、道具（よみどころ）に入れる。

**対応表と型ができれば、そこから先は道具がパソコンの中だけで書く。事業者さんの情報は Claude にもネットにも渡らない。**

## なぜ「一回で全部」なのか（2026-11-06 愛知の反省）

愛知は、注意事項だけを読んで申請書の対応表を作り、記載例を見ないまま渡した。そのあと「記号を使う」「説明は表の一番下」「概要の文も無い」「ダスト類は愛知の言い方」と、四回直すことになった。原因は三つ。

1. 記載例を手に入れる前に書き始めた（注意事項の文から書き方を推し量った）
2. 文字だけ読んで、記載例の**絵**（どのマスのどこに何が置かれているか）を見なかった
3. 申請書の一部の欄だけ対応表にして、残り（概要の文・表の列）を「あとで」にした

だからこの手順では、**記載例が無ければ始めない。全部の様式の全部の欄を一枚の分析表に書き切ってから、対応表と型を一度に作る。渡す前に記載例の絵と突き合わせる。** みゆきに渡すのは一回で済ませる。

## 0. 決まり（最初に必ず守る）

- 扱うのは **白紙の様式・公開の記載例・手引き・注意事項** と **架空の事業者（和歌山環境サービス株式会社・代表取締役 梅干し 太郎）** だけ。本物の事業者さん・依頼者の情報は、この手順に一切入れない。みゆきが本物の情報を貼ってきたら、使わずにそう伝える
- 様式・記載例のファイルは `手引き/<コード>_<県名>/様式/`・`手引き/<県>/` に置く。`app/` には入れない（県の著作物。`手引き/*/*` は git に入らない）
- 対応表（`app/data/様式/<コード>_<県>_<名>.yaml`）と型（`app/data/書き方の型/<コード>_<県>_<名>.yaml`）は、**みゆきが試しの下書きを Word・Excel で開いて「合っている」と言うまで**、道具に入れたことにしない（目録に足さない。コミットは手元の記録として残してよい）
- 県のサイトから取るのは、公開ページの普通のダウンロードだけ。ログインや申込みが要るページには入らない。**自動の取得を断るサイト（愛知など）は、くぐり抜けない。** みゆきにブラウザで落としてもらい、`手引き/<県>/` に写して `npm run 取得 -- <コード>` で登録する
- 道具は数字や事実を作らない。記載例の数字・社名・住所は型の文に入れない。聞いていない空きは「【要確認：見出し】」を残す
- 説明は日常語で。ツールを使うときは日本語で何をするか言う

## 1. そろえる（記載例が無ければ、ここで止まる）

1. `手引き/<県>/_出典.yaml` の `入口`・`入口の文書一覧`・`ファイル` を見る。無ければ `手引き/_出典候補_47_2026-11-02.md` と県のページ
2. 手引き（または提出書類一覧）の「申請に必要な書類」から、**新規・普通の産業廃棄物・収集運搬** で要る**様式を全部**拾う：申請書（様式第六号）、事業計画の概要（様式第六号の二）、別紙、誓約書、申立書、県独自の添付様式（誓約書・確認表など）。一つも漏らさない。様式ごとに「名前・ファイルの場所・形（docx/xlsx/doc/xls/pdf）」の表にする
3. 次の三つを**全部**手元に置く。足りないものがあれば、みゆきに「これを落としてほしい」と頼んで止まる。注意事項や手引きの文だけから書き方を推し量って先へ進まない
   - 白紙の様式（docx・xlsx）
   - **記載例**（申請書の記載例と、事業計画の概要の記載例。手引きの中の章でも、別の PDF でも、一括 zip の中でもよい）
   - 注意事項・手引きの「記入上の留意事項」
4. 取ってきたら `npm run 取得 -- <コード>` で登録し、txt にする。記載例の PDF は **ページごとに絵にもする**（`pdftoppm -r 110 -f N -l N -png`）。文字では分からないこと（印の説明がどのマスにあるか、品目名と印の間に空白があるか、行頭の字下げ）は絵で確かめる
5. 古い形（.doc・.xls）は、ここで止めてみゆきに伝える。保存し直すかはみゆきが決める。PDF だけの様式は書けない、と伝える

## 2. 分析表を書く（全部の様式、全部の欄）

`app/data/様式/<コード>_<県>_分析.md` を作る。これが「その申請書に何を書くべきで、どう書くべきか」の一枚で、対応表と型はここから機械的に作る。手本は `app/data/様式/23_愛知_分析.md`。

様式ごとに、**白紙の様式の欄を上から順に全部**並べ（`npm run 様式を診断 -- <様式> --詳しく` の出力を欄に区切る）、欄ごとに次を書く。

| 様式・面 | 欄 | 何を書くか | どう書くか（記載例の文そのもの） | 値の出どころ | 道具は | 出典 |
|---|---|---|---|---|---|---|
| 申請書 第1面 | 事業の範囲 | 積替保管の有無、品目、含む・除く、品目数、水銀使用製品 | `積替え、保管を除く／汚泥※▲、廃プラスチック類＊※、…／以上６品目（水銀使用製品産業廃棄物を含む。）／＊は自動車等破砕物を除く　※は…（以下同様）` | 控えの品目 | 書く | 記載例 p1 |
| 概要 第1面 | ２の表 運搬量 | t/月 または m3/月 | `20m3/月` | 聞き取り（品目ごとの運搬.運搬量） | 書く | 記載例 p4 |
| 概要 第4面 | 従業員数の内訳 | 人数の表 | | 事業者から聞く | 書かない（人数の表。行政書士） | 記載例 p7 |

「道具は」は三つのどれか：**書く**（控え・聞き取りから書ける）／**要確認を残す**（型の文は書くが事業者ごとに直す）／**書かない**（理由を書く。この理由がそのまま対応表の `書かない` と画面の案内になる）。「あとで」は無い。

分析表の頭には、県の決まりをまとめて書く。これは全部、記載例と注意事項から**引用で**裏を取る。

- **品目の書き方**：次のどれか。印（愛知：名前の後ろに ＊※■▲、最後に説明）／番号（和歌山：１．汚泥　２．…と【有・無】）／文（山形：「…を含む。」）／セル（奈良：Excel に「1、…以上N種類」）。締めの文（「以上○品目（…。）」の句点の有無まで）と、**印の説明をどこに置くか**（申請書は事業の範囲の末尾、概要は表のいちばん下の行、など）
- **品目の名前**：道具の名前（`品目たち`）と記載例・注意事項の名前を一つずつ見比べ、違うものを全部 `名前の言い換え` に書く（愛知：ばいじん→ダスト類、動物のふん尿→家畜ふん尿、ガラスくず等→「ガラスくず・コンクリートくず（…）及び陶磁器くず」）
- **含む・除く・だけ**：石綿・水銀含有ばいじん等・水銀使用製品・自動車等破砕物を、どの品目に、どう書くか。記載例に無い組み合わせ（「含む」の印が無い等）は作らず、要確認にする
- **概要の文の形**：全体計画（一つの文章か、品目ごとか）、具体的な計画（車両ごとか品目ごとか、時間・休業日の書き方、印の説明を書くか）、環境保全（(1)(2)(3) が一つのマスか別のマスか、箇条書きの句点の有無、「該当なし」の決まり）
- **申請日・宛先・事務所・事業場・施設の数量**の決まり（「申請日は空欄で持参」など）
- **書かない欄**とその理由の一覧

## 3. 対応表と型を一度に作る

分析表の「書く」「要確認を残す」の行を、漏れなく対応表と型に落とす。

1. 対応表（`app/data/様式/<コード>_<県>_<名>.yaml`）：方式（箱／段落／セル）を選び、`sha256`・`箱の数`（段落の方式は `段落の数`）で様式を固定する。書く場所ごとに `確かめ` を付ける。手本：和歌山（箱）、山形（段落）、奈良（セル）、愛知（段落＋印）
   - 品目の書き方は分析表どおり：`品目`（番号）／`品目の文`（文）／`品目の文`＋`品目の印`（印）／`品目のセル`（セル）。`品目の印` には印・説明の形・一行に何個・締め・`名前の言い換え` を書く。印の説明の置き場は `{品目の印の説明}`（表の行なら、いちばん下の行に）
   - 概要の表は、種類だけでなく運搬量・性状・排出事業場・積替保管の場所・運搬先の列まで `書く場所` にする（`{品目.N.運搬量}` など。和歌山の形で行が分かれる県は `{品目表.N.運搬量}`）
   - マスに空の段落が足りない様式（愛知の概要は2つ）は `文の欄` に `段落を増やす: true`。行数はマスの高さ（trHeight ÷ 行の高さ）から、一行の字数はマスの幅から決める
2. 型（`app/data/書き方の型/<コード>_<県>_<名>.yaml`）：**スキル「書き方を読む」（`kakikata-yomu`）の手順で**、分析表の「概要の文の形」から作る。全体計画・具体的な計画・環境保全の三つ全部。行ごとに `出典` と `写し` を付ける。差し込み口の id は `_共通の差し込み口.yaml` にそろえ、県独自の口は県コードを頭に付ける
3. 型が使う口と、対応表の `{型.…}`・`{品目.N.…}`・`{品目表.N.…}` が、画面の入力欄として出ることを確かめる（`様式が使う口`・`使う口` を node の小さなスクリプトで呼んで印字する）
4. `desktop/lib/shutoku.cjs` の目録に、県の `{ 短い名前, 名前, url, 入口, ファイル名 }` を足す。自動で取れない県は対応表に `自動で取れない` と `ファイルの場所`

## 4. 記載例と突き合わせる（自分で。みゆきに渡す前に）

1. 試しの下書きを作る：`cd app && npm run 下書きを試す -- <対応表> <様式> ../_申請/試し/<コード>_<県>_<名>_梅干し太郎の試し_<日付>.docx [型]`。品目を 2 つの試しと、**11 個選んだ試し**（印の全部、記載例に無い組み合わせ、名前の言い換え、表のあふれ）の両方
2. LibreOffice で PDF にし、`pdftoppm` で絵にして、**記載例の絵と同じページを並べて見比べる**。見るのは次の全部：
   - 置き場所（どのマス、何行目、字下げ）と並び順
   - 印・番号・句読点・括弧（「。）」まで）・空白の有無
   - 品目の名前（県の名前になっているか）
   - 印の説明の場所と並び（使った印だけ、記載例と同じ順）
   - 概要の文の組み立て（記載例と同じ見出し・同じ順）
   - 行数（表が次のページへ押し出されていないか、白紙のページが増えていないか：白紙の様式の PDF のページ数と比べる）
   - 要確認の文が、何をどう直せばよいか分かる日本語か
3. ほかの県の下書きが変わっていないこと：山形・和歌山（・奈良）の試しを直す前後で作り、`document.xml` の指紋（shasum）で比べる
4. `npm run 確認`・`npm run 見張り` を通す
5. 一つでも違えば、分析表に戻って直す。みゆきに「後で直す」と言って渡さない

## 5. みゆきに渡す（一回で）

- 分析表の場所と、県の決まりのまとめ（品目の書き方・名前・概要の文の形・書かない欄）
- 試しの下書きの場所（様式ごと）。「Word・Excel で開いて、欄の位置・記号・白紙のページ・字のはみ出しを見てください」
- 要確認を残した所と、その理由
- みゆきが直してほしいと言ったら、分析表から直して、もう一度渡す

## 6. 道具に入れる（みゆきが「合っている」と言ってから）

1. 目録に足したことを確かめ、`cd app && npm run 確認`・`npm run 見張り` を通す
2. 手元の記録（git）に残す。コミットの文は英語で「何ができるようになったか」
3. アプリを書き出し直す（`cd app && npm run build`、`cd desktop && npm run 写す && npm run 書き出し:win`）。公開版は `vercel` で出し直す（道具から止められたら、みゆきに `!` の一行を頼む）
4. `構成/_相談記録/` に、診断した様式・選んだ方式・みゆきが確かめた日・書かない欄を一枚残す

## 7. 報告する

- 〇〇県の様式（全部）：形、方式、書く欄、要確認を残す欄、書かない欄とその理由
- 県の決まりのまとめ（品目の書き方・名前の言い換え・概要の文の形）
- 試しの下書きの場所と、みゆきが確かめたか
- 次の県に回すときに効くこと（この県で初めて出た決まり。道具に足した仕組み）
